# AI 技能（Skill）入门教程

欢迎加入！这份教程介绍组里给大家准备的 AI 技能包：技能是什么、怎么安装、怎么使用，以及以后怎么自己创建技能。读完大约 15 分钟，建议边读边在自己的 Claude Code 或 Codex 里试一下。

## 1. 技能是什么

技能（Skill）是写给 AI 的一套**固定工作流**，并带着完成这项工作需要的资料和工具。比如“提 PR 前自检”技能规定了先查范围、再实跑测试、再找新上下文审查、最后写风险与回滚说明，还附带一个检查改动范围的脚本。装好以后，你只要说“准备开 PR”，AI 就会按这套流程做，而不是每次临场发挥。

一个技能就是一个文件夹：

```
my-skill/
├── SKILL.md          # 入口：什么时候用、按什么步骤做、细节去哪里找
├── references/       # 参考资料：详细规范、检查清单、领域知识、案例
├── scripts/          # 脚本：重复且确定的动作交给代码，不靠 AI 每次重写
└── assets/           # 模板与素材：报告模板、代码骨架、图片样式等
```

### 渐进式披露：AI 按需读取

技能不会一次性塞进 AI 的上下文，而是分三层读取：

| 层级 | 什么时候读 | 内容 |
|---|---|---|
| 1. 描述（description） | 每次对话都在，只有一两句 | 这个技能做什么、什么说法会触发它 |
| 2. `SKILL.md` 正文 | 任务匹配时才读 | 工作流步骤、判断规则、去哪个 reference 找细节 |
| 3. `references/`、`scripts/`、`assets/` | 走到具体步骤时才读或运行 | 详细知识、代码、模板 |

所以一个技能可以带很多资料，却不会拖慢平时的对话。

### 技能不是提示词模板

这是最容易误解的一点。提示词模板只是一段写好的话；技能的核心价值是**固定的工作流**，以及支撑工作流的 **references**：

- `SKILL.md` 用 Markdown 写自然语言的流程，相当于目录和调度：先做什么、遇到什么情况读哪份资料、做到什么程度算完成。它里面也会有提示词，这部分重要，但它是辅助。
- `references/`、`scripts/`、`assets/` 用文档、代码和模板保存真正的“做法”：检查标准、领域经验、可运行的脚本、可复用的模板。这才是技能最有价值的部分。

两者相辅相成：流程告诉 AI 怎么走，资料保证每一步都做得对、做得一样。只把一段提示词存成 `SKILL.md`，算不上好技能。

### 技能和 MCP 的区别

| | 技能（Skill） | MCP |
|---|---|---|
| 是什么 | 一套工作流和资料，AI 读了照着做 | 一个工具接口，AI 调用它拿结果 |
| 运行在哪 | 你本机，AI 直接读取文件 | 可以在远程服务器上 |
| 是否可闭源 | 不能：AI 必须读到内容才能执行，所以技能内容对使用者是公开可见的，通常直接开源 | 可以：服务端代码可以是别人的、闭源的，你只看到接口 |
| 适合 | 怎么做一件事（流程、规范、经验） | 能做什么事（查数据库、调外部服务） |

技能也可以通过 API 调用闭源服务（例如某一步调用一个在线接口），但这种情况比较少。大多数技能是开放的说明、资料和脚本。两者经常一起用：技能规定流程，流程中的某一步调用 MCP 工具。

## 2. 安装

需要 Claude Code 或 Codex（两者都装也可以），以及 git、Python 3.10 以上。

```bash
git clone https://github.com/YonganZhang/student-ai-skills.git
cd student-ai-skills
bash install.sh --dry-run    # 先看会做什么，不改任何文件
bash install.sh              # Claude Code 与 Codex 两端都装
```

- 装完**新开一个会话**才生效。Claude Code 里输入 `/skills` 可以看到已装的技能。
- **`dev-pr-self-check`（提 PR 前自检）是必装技能**，安装脚本一定会装上。参与组里项目开发的同学，PR 描述里必须贴它生成的自检报告。
- 用浏览器自动化技能还要装：`npm install -g @playwright/cli`（或安装时加 `--with-playwright`）。
- 更新：在仓库目录 `git pull`，再运行 `bash install.sh --force`。

## 3. 怎么使用

**用平常的话说需求就行，不需要背技能名。** AI 会根据描述自动选择技能。也可以直接点名，例如“用 grill-to-spec 帮我把需求问清楚”。

| 你想做的事 | 可以这样说 | 会用到的技能 |
|---|---|---|
| 开 PR 前检查 | “我改完了，准备开 PR，帮我自检” | `dev-pr-self-check`（必装） |
| 建项目计划、记进度、交接 | “帮我给这个项目建个计划”“现在做到哪了” | `share-top`（附 `plan` 命令） |
| 把模糊需求问清楚 | “盘问我，把这个功能的需求问清楚” | `grill-to-spec` |
| 审别人的代码 | “帮我审一下这个 PR” | `share-code-review` |
| 找现成的库 | “有没有现成的库能做 OCR” | `dev-find-wheels` |
| 做 PPT 或方法图 | “把这张图转成可编辑 PPT”“画个方法思维导图” | `real-ppt`、`pptx-gen`、`share-technical-roadmap` |
| 前端界面美化 | “美化这个后台页面”“做个落地页” | `frontend-design`、`design-taste-frontend` |
| 操作网页、做网页验收 | “打开这个网址把表填了并截图” | `playwright-cli` |
| 深度学习实验 | “模型过拟合了怎么办”“把这篇论文的模块接进我的网络” | `share-autoresearch-engine`、`mlgain-integrate-component` |
| 给项目装专用能力 | “这个项目要装什么技能” | `share-project-provision` |
| 自己创建或改进技能 | “帮我把这个流程做成一个技能” | `share-skill-creator` |

### 一个完整的例子：提 PR 前自检

1. 改完代码并提交到自己的分支后，对 AI 说：“准备开 PR，目标分支是 upstream/master，帮我自检。”
2. AI 会运行检查脚本，列出改了哪些文件，提醒疑似密钥、大文件和高风险路径。
3. AI 会跑项目要求的测试和构建，保留命令与输出；跑不了的会如实写进“未验证”。
4. AI 会让一个不带当前对话历史的审查者看你的改动，把问题分成“重要 / 小问题 / 已有问题”。
5. 每条问题要么修掉，要么写明不修的理由。
6. 最后 AI 给出一份自检报告，第一行是待修问题数。把它连同测试、风险、回滚说明贴进 PR 描述。

### 使用时的几个习惯

- 结论看证据：AI 说“测试通过”时，要看到实际命令和输出。
- 技能给的是流程，不替你做决定：选型、范围、是否合并，最终由你和负责人决定。
- 觉得某个技能不好用、或者选错了技能，直接告诉 AI，也欢迎在技能帖里反馈。

## 4. 自己创建技能

包里的 `share-skill-creator`（技能创建器）专门用来创建、修改和评估技能。以后你发现自己在重复做同一类工作，就可以把它沉淀成技能。

### 什么时候值得做成技能

- 同一类任务做过三次以上，而且每次步骤基本相同；
- 有一套必须遵守的标准或检查项（例如实验记录格式、出图规范）；
- 有可以复用的资料、脚本或模板。

一次性的小任务、只是想换个说法的提示词，不需要做成技能。

### 用技能创建器创建技能

对 AI 说：

> “我每次处理实验数据都要做这几步：检查缺失值、统一单位、画分布图、写一段数据说明。帮我做成一个技能。”

技能创建器会带着 AI 完成：

1. **问清目标和边界**：什么时候触发、什么时候不该触发、做到什么程度算完成。
2. **设计结构**：`SKILL.md` 只写流程和指路；检查标准、单位换算表放进 `references/`；画分布图、检查缺失值这类确定的动作写成 `scripts/` 里的脚本。
3. **写描述**：一两句话写清“做什么 + 常见说法”，必要时加“不触发：……”，避免和相近技能混淆。
4. **验证**：用几句真实的说法测试能不能正确触发，再用几句相近但不该触发的说法测试会不会误触；脚本要有测试。
5. **迭代**：真实用过几次后，把发现的问题补进 references 或脚本，而不是把 `SKILL.md` 越写越长。

一个最小的技能长这样：

```markdown
---
name: lab-data-check
description: "实验数据预处理：检查缺失值、统一单位、画分布图并写数据说明。触发：处理实验数据、数据预处理、检查这批数据。不触发：模型训练（走深度学习技能）。"
---

# 实验数据预处理

1. 运行 `scripts/check_missing.py <数据文件>`，报告缺失与异常值。
2. 按 `references/units.md`（单位换算表）统一单位，换算记录写进说明。
3. 运行 `scripts/plot_dist.py` 画每列分布图。
4. 按 `assets/data-note.md`（数据说明模板）写说明，列出处理过的列和未解决的问题。

完成标准：说明文档、分布图、清洗后的数据三者齐全，且说明里的数字与脚本输出一致。
```

注意这个例子里，`SKILL.md` 只有流程和指路，真正的知识在 `units.md`、脚本和模板里。

### 技能放在哪

| 用途 | 位置 |
|---|---|
| 只给自己用、跨项目通用 | Claude Code：`~/.claude/skills/<技能名>/`；Codex：`~/.agents/skills/<技能名>/` |
| 只属于某个项目、和队友共享 | 项目里的 `.claude/skills/<技能名>/`（Codex 读 `.agents/skills/`，可以软链到同一份） |

项目技能跟着代码一起进 Git，队友拉下代码就能用。改项目技能和改代码一样，要走 PR。

### 常见误区

- 把技能当成长提示词，所有细节都堆进 `SKILL.md`。正确做法：入口保持简短，细节放 references，确定的动作写脚本。
- 描述写得太宽（例如“处理数据”），结果什么任务都触发它。描述要写清触发说法和不触发的边界。
- 只写不测。至少用几句真实说法验证触发，用一次真实任务验证效果。
- 技能里写本机路径、账号、密码。技能会被分享，凭证一律不进技能。
