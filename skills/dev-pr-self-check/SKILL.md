# 提 PR 前自检

目标：让审查者花最少的时间，也不增加回滚和事故。发起改动的人负责向审查者讲清验证证据和影响；出了回归，配合定位、修复或回滚。结论只认本轮实际跑出的证据，不认“应该没问题”。

## 何时用

- 代码或文档改动准备开 PR、往已有 PR 推新提交、请求合并之前。
- PR 收到审查意见、要再推一版之前（回到第 5 步）。
- 普通进度说明、只读问答不走整套流程。只审别人的改动走 `dev-code-review`。

## 六步

1. **范围**：一个 PR 只做一件事，能单独回滚。先 `git status --short` 看工作区；无关文件和别人的改动只是不放进这次提交，保留在工作副本里，不要删除、还原或替别人 stash。然后在待提 PR 的仓库根目录运行本技能目录下的脚本：`python3 "<本技能目录>/scripts/scope_check.py" --base <PR 目标分支>`（目标分支按项目约定确认，不默认猜 main）。它只检查已提交的内容，列出改动文件、行数、疑似凭证、大文件和高风险路径；它是启发式检查，0 个 blocker 不等于没有密钥。发现已提交的凭证：停下，告诉负责人去作废更换，只删文件不算处理完。改动过大先提拆分方案。
2. **实跑检查**：先读项目的贡献说明和 CI 要求，跑它要求的测试、构建、lint、类型检查，再加和这次改动相关的行为验证；保留命令和关键输出，不适用的写“N/A：理由”。修 bug 要证明测试在旧代码上失败、新代码上通过（旧代码在临时工作树里跑，不覆盖当前工作区）。用户能看到的行为走真实入口（截图、Playwright、真实 API 调用）。跑不了的写进“未验证”。
3. **新上下文审查**：让一个不继承你会话历史的审查者看改动；它可以读整个仓库和需求，但拿不到你的推理和“我觉得没问题”。做法和审查提示见 [新上下文审查](references/fresh-review.md)。涉及权限、凭证、外部输入、路径或命令拼接的，再做一轮安全审查。
4. **定风险档**：按“坏了会怎样”定档，不按作者是谁、也不只看文件类型；见 [风险分级](references/risk-tiers.md)。高风险在 PR 里写明并交负责人审；AI 的“通过”不算人工批准。
5. **处理意见，收敛轮次**：每条意见要么修掉，要么写明不修的理由（误报、有意为之、已有问题另开 issue）。同一类问题一次修全。之后每轮核对修复的 diff、所有未决意见和受影响的调用链；到第三轮仍有未解决的重要问题，停下来重新设计、拆 PR 或请负责人介入，不再硬改；轮次上限不豁免重要问题，要带着它合并须负责人明确接受风险。
6. **写 PR 描述**：按 [PR 描述模板](references/pr-template.md) 写清做了什么、为什么、怎么测的、风险、怎么回滚、哪些没验证。项目有自己的 PR 模板时以项目模板为准，把缺的几项补进去。

推了新提交，旧证据只对旧提交有效：记下证据对应的提交，重跑受影响的检查；依赖、构建配置或公共接口变了，扩大重跑范围。

## 自检报告

开 PR 或回复审查前给出报告，第一行是数量：

```
自检：0 个待修问题（或：2 个待修，1 个已说明不修）
范围：N 个文件 +A/-D（<base>..<head 提交>）；风险档：低/中/高（理由）
已跑：<命令> → <结果>；N/A：<项>：<理由>
新上下文审查：重要 X / 小问题 Y / 已有问题 Z，处理情况…
未验证：…
```

没有问题就直说“0 个待修问题”，不要凑小问题。每条问题带文件和行号。

## 把重复问题修在源头

同一类意见第二次出现，缺的是规则或检查：能写成测试、lint 或脚本检查的优先写成检查；属于项目约定的，提议补进项目的 `AGENTS.md`/`CLAUDE.md` 或 `REVIEW.md`（审查说明：本仓库什么算失败、哪些路径跳过、哪些小问题不报）。改规则文件先征得项目负责人同意。

## 边界

- 只覆盖作者侧。CI、安全阻断、负责人审批、合并队列、灰度发布由项目维护；项目要求更严时以项目为准。
- 不自动推送、开 PR 或合并；这些按用户或项目的授权执行。
- 来源与本技能的取舍见 [sources.md](references/sources.md)。
