# 新上下文审查

写代码的会话容易默认自己的思路是对的。换一个不继承这段历史的审查者，能减少“以为做了、其实没做”的漏洞，但它也会出错，结论要核实。

## 怎么起一个新上下文

先确认命令在你的版本里可用（输入 `/` 看菜单）；不可用就用最后一行的办法。

| 环境 | 做法 |
|---|---|
| Claude Code | 在项目里运行 `/code-review`，确认审查范围是这次的分支或 diff；涉及安全再运行 `/security-review`。只要报告，不加自动修复或发评论的参数。也可以派一个子智能体，只给它下面的审查说明 |
| Codex | 运行 `/review`，选与自检一致的范围（对比目标分支）；要确定的命令行入口用 `codex review --base <目标分支>`，未提交改动用 `codex review --uncommitted`。要用自定义审查说明时另开新会话，不和这些选项拼在一起 |
| 都没有 | 新开一个会话，粘贴下面的审查说明，让它自己在仓库里跑 `git diff` 并读相关文件 |

子智能体如果默认继承当前对话，要显式只给审查说明；不能认为“开了一个 agent”就已经隔离。

## 审查说明（复制后填空）

```
你是这次改动的独立审查者，只读，不改文件。
需求：<一两句话，或 issue/规格链接；有验收标准就贴上>
目标分支：<base>，改动：<head 提交>
先运行 git diff <base>...<head>，再按需要读相关调用方、被调用方、AGENTS.md/CLAUDE.md、REVIEW.md 和测试。
测试证据：<命令与结果；界面改动附截图>

1. 逐条对照需求，列出没做到或做偏的地方。
2. 只报会导致行为错误、破坏接口约定、泄露数据或越权、丢数据、让测试失去意义的问题。
   每条给：文件:行号、会怎样出错（具体输入或场景）、证据（代码引用或复现命令）、建议的验证方式。
3. 分级：重要（合并前必须处理）/ 小问题（可选，最多 5 条，格式和命名偏好不报）/ 已有问题（不是本次引入，单列）。
4. 只看 diff 判断不了的，写明缺什么上下文。
第一行写数量，例如“重要 0 / 小问题 2 / 已有问题 1”；没有重要问题就直说。
```

## 安全审查补充

改动涉及登录与权限、凭证与密钥、用户上传或外部输入、拼接 SQL/命令/路径、反序列化、对外请求、日志里的个人数据时，专门过一遍，重点问“谁能借这个改动做原本做不到的事”。

## 收到结果后

- 到代码里核实每一条；确认是误报的写明理由。
- 下一轮交给审查者：修复的 diff、所有未决意见、受影响的调用链。已解决且没有回归的不再重复报；出现新证据或回归可以重新打开。
