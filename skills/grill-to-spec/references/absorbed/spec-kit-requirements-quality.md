# 复杂功能的需求质量检查

## 何时使用

已经需要写 spec，且包含多个独立要求、跨组件契约或相互影响的失败状态时，在交给实现前检查一次。明确的小修改沿用原有验收，不补模板、不为凑编号追问用户。

## 检查内容

1. 每项要求说明使用者、触发条件、可观察结果；“快、清晰、可靠”如影响验收，需有可检查的标准，不能擅自编造数值。
2. 只检查相关边界：空输入、失败、取消、重试、重复提交、状态过期、权限或部分成功；不要求每个功能覆盖所有类别。
3. 分开记录功能要求、验收条件、假设和非目标。业务效果指标不能冒充已实现的能力，预期科研增益不能当成真实实验结果。
4. 对照已有决定，找矛盾、重复和会改变实现的缺项。先查文件与现有代码，只问实质影响正确性或范围、且现有信息无法回答的问题；已有授权不再询问。
5. 把关键要求写成可追踪条目。优先复用现有编号；没有编号且需要跨任务引用时，才在 spec 内分配局部稳定的 `R1`、`R2`。外部引用使用 `spec路径#编号`，不重编号已有条目。

复杂 spec 可按需使用以下形状，不重复已有同等内容：

| 要求引用 | 条件与用户可见结果 | 验收方式 | 未决问题或假设 |
|---|---|---|---|
| 本 spec 的 R1 | 当……时，用户能看到…… | 操作……并检查…… | 仅保留影响实现的事项 |

检查通过只表示需求足够明确，不表示功能已实现、测试已通过或业务效果已达成。未决问题只阻塞受影响部分，独立且已明确的部分可继续。

## 输出与落点

沿用项目已有 spec 真源，明确记录检查范围与仍未决事项；短检查可以只在回复中说明。已有批准的 spec 或实现范围内补充，无需新增确认环节；新产品取舍遵循原有授权边界。

需求到任务和证据的关联由 [TOP 覆盖核对](../../../share-top/references/absorbed/spec-kit-coverage.md) 负责，不在这里维护第二份任务状态。

## 验证边界

- 正例：额度耗尽时的展示要求必须说明它与“处理中”的优先关系，以及恢复后何时更新；不能只写“状态显示正确”。
- 近误触反例：将已有文字颜色改成明确指定的黑色，不额外生成 spec、编号或问卷。
- 不把完成本清单当成功能验收，不为无关类别补空章节。
