# CLI 创建与接口规范

为人和自动化提供可发现、可验证的命令入口。统一基本契约，架构按任务选择；已有 CLI 优先沿用其框架与兼容契约。一次性命令不必包装成产品。

## 开始前

读 [设计合同](references/design-contract.md)，确认真实消费者、现有真源、读写边界和验收。先查已有官方工具、项目接口和仓库模板；一个稳定业务函数加参数解析足够时，不引入框架、服务或数据库。

| 场景 | 做法 |
|---|---|
| 少量内部命令、无第三方依赖需求 | 标准库；Python 可复用 [轻量母模板](assets/python-minimal/README.md) |
| 可分发 Python 包、多子命令 | 已有框架优先；新项目可用 [Click 发布母模板](assets/python-click/README.md)，Typer 按团队习惯评估 |
| TypeScript、多命令、插件或发布体系 | 评估 oclif；已有 Node 项目沿用现有工具 |
| 多个生成项目需要持续升级母模板 | Click 母模板用 Copier 追踪；更新后检查冲突、测试和构建 |

框架选型见 [上游选型](references/upstream-options.md)，已吸收部分见 [来源与取舍](references/absorbed/upstream-cli-patterns.md)。依赖按需装进项目或任务环境。

## 所有稳定 CLI 的基本交付

- `--help` 有可运行例子；调用入口、README 与源码都在受 Git 管理的所属仓库。
- README 写清用途、安装、最短调用、输出、退出码、读写边界、验证方法。缺项可复用 [文档骨架](assets/README.template.md)，已有文档按原结构补齐。
- 自动化调用有非交互路径，诊断走 stderr；程序消费者用稳定机器输出，不解析展示文字。`--json` 按消费者需要实现，不把文件下载或二进制流强行包成 JSON。
- 退出码与部分失败有明确契约；既有消费者不因统一风格而被破坏。新工具默认 0 成功、1 运行/业务失败、2 用法错误。
- 验证实际行为：正常结果、错误输入及失败状态；机器模式检查可解析性、通道和退出码。help 成功不等于业务成功。

## 按需能力

写入：复用既有真源，按影响决定预览和确认；涉及多写者时才加锁/事务与版本冲突处理。需要外部回执的操作验证实际生效，不把发出请求当成功。

跨项目定位、分页/输出上限、token 比较、兼容转发、安装短入口、认证与远端超时按消费者选用；不要求每个工具全套配齐。完整边界在设计合同中。

## 母模板的使用与维护

1. 小型 Python 工具复制 `assets/python-minimal/` 到项目内的新目录，不覆盖现有文件；改成真实业务，更新 README 和测试。
2. 在项目记录母模板路径和共享仓库提交号，生成物独立维护；禁止运行时软链到全局母模板业务代码。
3. 可分发包走 Click 母模板的生成、安装和升级流程；打包仅在此档启用。写入保护、服务层按需设计。
4. 轻量档验收：`python3 -m unittest discover -s <复制目录>/tests -v`；Click 档按模板 README 跑 pytest、打包与安装验证，再跑真实消费者。

## 让其他 AI 找到它

将命令登记在项目 README 或所属业务 skill 的入口索引，细节留在同一份 CLI 文档。只有每轮都需要的核心入口才进全局规则或 hook；不为每个 CLI 添加常驻提示，也不自动为每个 CLI 新建 skill。本技能负责创建 CLI，业务技能负责使用其命令。
