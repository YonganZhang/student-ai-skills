# 从问题到流水线：把“水面下”的坑变成默认检查

目标不是写更多 checklist，而是让同类问题**第二次不再靠人记得**。路径：

> 现象 → 证据 → 根因层 → 不变量 → 检查 → 自动化/门禁 → 回归 → 复盘

只有走到“回归”和“默认流程”，才算固化；只写一条“注意 XX”不算。

## 1. 什么算“水下问题”

满足任一条件：

- 结果看起来正常，但结论可能错（泄漏、选择噪声、评价器 bug）；
- 训练能跑，但机制不成立（初始化/梯度/归一化/尺度错位）；
- 指标涨了，但成本/稳定性/可复现性变差；
- 同类事故第二次出现；
- 换一个人/AI 就会再犯；
- 论文/比赛方案有效，但不知道怎么迁移或验证。

“loss 不降”“报错”通常是水面上的；水下问题更常见的是：**实验能跑、数字好看、结论不可信**。

## 2. Issue ledger：先记录，再修

每个问题一条记录，使用 `schema_version: 1` + `issues` 列表；不要只留在聊天或一段散文里。

最小字段：`id, title, status, severity, blocks_action, layer, symptom, evidence, root_cause, invariant, check, automation, owner, opened`。`evidence` 必须是 `path/fact` 列表；`closed` 还要 `close_evidence, closed_by, reviewed`。

可直接复制 [issue ledger 模板](../assets/issue-ledger.template.yml)；已填写的关闭示例见 [example](../assets/issue-ledger.example.yml)，校验命令 `python scripts/issue_ledger_check.py <ledger.yml> --strict`。

字段不是形式：**evidence 必须能指向文件/行/数字**；root_cause 写到层，不写“模型不行”；check 要能执行；regression 要能在 CI 或固定入口复现（做不到就写手动复核）。

## 3. 分层定位

| 层 | 典型水下问题 | 先查 |
|---|---|---|
| 任务/指标 | 指标定义和部署目标不一致；阈值/匹配/聚合错 | 评价器源码、真值对真值、空/全背景的适配器定义 |
| 数据 | 泄漏、错标、空标、重复、分布偏移、预处理统计用全量 | split、叠图、标签分布、近重复 |
| 模型 | 通道/尺度/语义错位、初始化破坏父模型、梯度断路 | shape 断言、step0 等价、梯度范数 |
| 训练 | lr/warmup/AMP 不稳、BN 统计轴/每卡样本不足、loss 尺度、梯度冲突 | 曲线、记忆/学习探针、激活/梯度统计 |
| 选择 | 验证集用旧、候选差异接近噪声、test 回流、阈值过拟合 | 选择日志、候选数、seed/单位方差 |
| 评测 | 评测脚本版本错、后处理不一致、单位/坐标换算 | 冻结父模型重算、阳性对照 |
| 部署 | 预处理/通道/分辨率不一致、延迟/显存超预算 | 端到端推理对拍、profiling |
| 流程 | 缺回执、配置漂移、无法续跑、结果覆盖 | manifest、hash、resume 测试 |

先定位层，再谈修法。层错，修得越多越偏。

## 4. 从根因到不变量

把根因写成一句**可证伪的不变量**：

- “同一患者不能跨 split”；
- “新模块在 step 0 关闭时输出必须等于父模型”；
- “test 不能出现在选择日志里”；
- “best 必须来自 select 段；候选接近时结论写无法区分，不强制拉开差距”；
- “同主预算轴比较必须记录样本曝光/updates/FLOPs/时间，cap 命中标右删失”。

不变量要满足：**能判定真假、能自动检查、失败时能定位**。做不到就先降级为人工检查，并写清为什么不能自动化。

## 5. 选择检查位置

检查要放在**最早能发现且成本最低**的位置：

| 位置 | 适合抓什么 | 代价 |
|---|---|---|
| 设计时（写实验单） | 假设不清、对照缺失、预算不匹配 | 最低 |
| 数据加载前 | split 泄漏、标签/通道/尺寸错 | 低 |
| 首个 optimizer.step 前 | 结构判断、初始化、优化器成员、shape | 低 |
| 第一个 epoch/batch | 记忆探针、梯度、BN 统计轴、loss 下限 | 低 |
| 第一次验证 | 选点、曲线、指标口径 | 中 |
| 扩大预算前 | 信号是否真实、是否 cap、方差 | 中 |
| 冻结/test 前 | 选择回流、manifest、回执 | 高（但必须） |
| 负结果后 | 工程失败 vs 方向失败 | 中 |

**不要把所有检查都塞到最后。** 越晚越贵，越容易用“再跑一次”掩盖问题。

## 6. 自动化的四个等级

1. **断言**：入口/训练脚本里 `assert`，失败即停；适合 shape、split、step0、optimizer 成员。
2. **脚本检查**：独立命令，输出机器可读结果；适合曲线、manifest、泄漏、选择日志。
3. **门禁**：训练/评测入口在关键动作前调用，失败拒绝启动；只适合“必须阻止”的结构/预算/test 边界。
4. **回归测试**：CI/本地测试固定反例；适合“曾经出过的事故”。

优先 1/2，只有“必须阻止”才上 3。门禁太多会逼人绕过；门禁要有明确错误码和修复路径。

## 7. 把一次事故变成回归

最小回归三件套：

- **反例输入**：能触发旧 bug 的数据/配置；
- **失败断言**：旧代码必须失败，新代码必须通过；
- **修复说明**：根因、影响范围、兼容性。

没有反例的“修复”不可信；没有失败断言的测试只是 smoke。只有可复现的软件缺陷要求“旧代码失败/新代码通过”；方向性负结果写边界即可。

## 8. 复盘问题

关闭 issue 前回答：

1. 这个问题影响过哪些结论/提交？要不要更正？
2. 是否有其他项目/任务共享同一根因？
3. 检查是否覆盖“实现失败”和“方向失败”两种情况？
4. 检查本身有没有误报/漏报？有没有反例测试？
5. 是否改变了默认流程/模板/合同？谁维护？
6. 下一次同类问题，AI/新人能不能在 5 分钟内发现？

## 9. AI 在固化中的角色

- **Scout**：从错误切片、比赛复盘、论文/issue 里找候选问题；
- **Auditor**：核对证据、复现、检查是否真的触发；
- **Red Team**：尝试绕过检查、构造反例；
- **Scribe**：把修复写成 issue/回归/文档；
- **Supervisor**：确认关闭条件，不代替作者修。

不要让同一个 AI 既提问题又宣布“已修复”；至少一个独立检查点。详见 [AI 检查点](ai-checkpoints.md)。

## 10. 最小落地模板

```text
现象：
证据（文件/数字）：
层：
根因：
不变量：
检查命令：
失败时错误码/提示：
回归测试：
影响的历史结论：
负责人/复核人：
```

先填这张表，再改代码。填不出来，说明还没定位，不要用“加个模块/多跑几组”掩盖。
