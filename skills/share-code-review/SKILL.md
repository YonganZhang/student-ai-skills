# 代码审查

目标不是堆积 nit，而是尽早发现会改变行为、破坏契约或增加长期维护成本的事实性问题。

## 按任务选择模式

| 任务 | 读取 |
|---|---|
| 普通改动审查 | 下方工作顺序 |
| 简化代码、过度设计、无用抽象 | 下方工作顺序第 3 步（专门的简化审计流程（可选，本包未包含）） |
| 明确要求多轮，或较大阶段的分批审查 | 按阶段拆分后逐批使用下方工作顺序（专门的多轮审查流程（可选，本包未包含）；外部模型复核可用外援审查技能（可选，本包未包含；公开版见 https://github.com/YonganZhang/external-review-skill ）） |
| 作者提 PR 前自检（实跑检查、风险档、回滚说明） | [提 PR 前自检](../dev-pr-self-check/SKILL.md) |

审查方式与提供方沿用用户要求；合并入口不默认启用多轮、子智能体或外援。

## 工作顺序

1. 先确认当前分支、基线、工作区状态和用户要求的改动范围。只审查已声明的范围；范围不清时先标注不确定性。
2. 从入口追到消费者，再从接口回看另一侧：字段、状态、错误、所有权、取消、超时、释放和版本兼容都要成对检查。
3. 检查生命周期、并发、重试/取消、资源释放和真实生产入口。新增抽象必须有生产消费者；测试、文档或示例单独使用不算生产消费者。
4. 选择与 diff 相关的最小验证集。UI/API/模型输出变化要有对应的行为证据；不要用无关的全量测试掩盖未验证的关键路径。

复杂功能交付或用户要求对照需求查漏时，按 [需求收尾核对](references/absorbed/spec-kit-convergence.md) 检查约定范围内的当前实现；普通小 diff 不额外展开此流程。审非小型分支或 PR 时，按 [两轴审查](references/absorbed/mattpocock-two-axis-review.md) 分别核对"规范"和"需求"：没有需求来源就标明并只跑规范轴，没有成文规范仍用坏味道基线；两轴结果分列不混排。

## 报告格式

每个 blocker 必须包含：位置、影响、可复现或静态证据、建议的验证方式。优先报告一个有证据的 blocker，而不是罗列审美 nit。按 `blocker / important / suggestion` 分级；没有证据就不要升级严重性。

同时检查新增文字是否泄漏设计会话、变更叙事或重复解释；保留契约、前后置条件、审计证据和历史决策，不改写成空洞口号。

审查结束时给出：已验证范围、未覆盖范围、最小下一步。仅审查请求不自动修改文件；已有修复或优化授权时，由主控核实后按约定时机修改并验证，不重复请求批准。多轮审查须收齐指定报告后统一处理。
