# 两轴审查：规范 vs 需求

触发：审一个非小型分支、PR 或阶段性改动。小 diff 不展开。

## 步骤
1. 钉住范围：先确认基线 `git rev-parse <基线>` 能解析，再按要审的内容选一条 diff——已提交的分支/PR 用 `git diff <基线>...HEAD`，含未提交改动用 `git diff <基线>`（新增未跟踪文件另列），只审暂存区用 `git diff --cached`。两轴拿同一份冻结的范围；坏 ref 在这里报错，所选范围为空就报告"无改动"，不派子 agent。
2. 找需求来源：提交信息里的任务/issue 号 → 用户给的路径 → TOP 计划、`_wiki` 或 specs 目录中与分支同名的文档 → 问用户。确实没有就跳过需求轴，并在报告里写明。
3. 找规范来源：AGENTS.md、CONTRIBUTING、CODING_STANDARDS、项目 lint 配置；一份都没有时规范轴只用下方坏味道基线。
4. 为有材料的轴各派一个只读子 agent（两轴都有时并行），各自只拿本轴材料；两者都仍按 SKILL.md 追接口两侧与真实消费者，按需读最小相关上下文：
   - 规范轴：diff 命令、提交列表、规范文件、下方坏味道基线全文。逐处报告违反的成文规范（引用规范原文）和疑似坏味道（引用 hunk）；成文规范可判硬伤，坏味道一律标"可能"；工具已强制的不报。400 字内。
   - 需求轴：diff 命令、提交列表、需求全文。报告缺失或只做了一部分的需求、需求之外的行为（范围蔓延）、看似实现但做错的地方，每条引用需求原文。400 字内。
5. 汇总：`## 规范`、`## 需求` 两节分列，不跨轴合并重排；每轴内部仍按 blocker / important / suggestion。结尾一行：各轴条数和各轴最严重的一条。

## 坏味道基线（Fowler《重构》第 3 章；仓库成文规范优先）
名字说不清用途 → 改名 | 同一逻辑出现在多处 → 提取共用 | 方法总在用别的对象的数据 → 搬过去 | 几个字段或参数总一起出现 → 合成一个类型 | 用字符串或原始类型表示领域概念 → 给它一个小类型 | 同一个 switch/if 链在多处重复 → 多态或共享映射 | 一个逻辑改动散落到很多文件 → 收拢到一个模块 | 一个文件因多个无关原因被改 → 按变化原因拆 | 为不存在的需求加的抽象、参数、钩子 → 删掉并内联 | 长链 `a.b().c().d()` → 在第一个对象上包一层 | 只做转发的类或函数 → 去掉，直接调目标 | 子类拒绝继承来的大部分行为 → 改用组合
