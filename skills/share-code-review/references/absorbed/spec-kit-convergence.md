# 复杂功能的需求收尾核对

## 进入条件

复杂功能已经实现、准备交付，或用户明确要求对照需求查漏时使用。范围来自已批准 spec、决定、任务与验收；只看相关当前实现，不把普通小 diff 审查扩成全项目检查。没有正式 spec 时可用已确认的需求和验收，不为审查补造整套文档。

普通 diff 审查仍负责本次改动风险；本检查补充“约定需求是否在当前实现中成立”。任务打勾、AI 自报、命令退出码或静态阅读无发现，都不能单独证明用户行为可用。

## 核对过程

1. 固定本次需求范围、相关代码版本或工作区状态、验收环境。现行需求以用户已批准的最新决定为准，旧 spec 冲突先标明，不默默修改需求来迎合代码。
2. 按要求查实际入口、实现和消费者；没有搜到符号只代表证据不足，不能直接判定未实现。
3. 对发现分类，并沿用主技能的 `blocker / important / suggestion` 严重程度，不新增评级体系：

| 缺口类型 | 判断依据 |
|---|---|
| 未实现 | 经相关入口与消费者核对，约定能力不存在 |
| 部分实现 | 存在实现，但缺少约定分支、状态或边界行为 |
| 与要求冲突 | 当前行为与已批准要求或契约不一致 |
| 超出范围 | 工作缺少已批准要求、必要依赖或技术约束依据；先请求说明，不自动删除 |

4. 每条发现给需求引用、代码位置或实际行为证据、影响，以及最小验证方式。实际运行缺失、环境不可用或结果无法匹配当前实现时，单列“未验证”，不混入“未实现”。
5. 按改动和风险选择必要的行为验证，复用能证明仍有效的已有结果。需求文字清楚、测试存在、关联表填满都不能替代实际证据。

报告可复用主技能的审查格式，只增加“需求引用 / 缺口类型”；关联表和任务状态归 [TOP 覆盖核对](../../../share-top/references/absorbed/spec-kit-coverage.md)，本文件不维护台账。

## 结论与后续

- 明确已核对范围、证据支持的结论、缺口和未验证部分。无缺口但缺运行证据时只能说“本次静态核对未发现缺口，运行验收未完成”。
- 需求检查发现问题不等于可随意改产品。纯审查任务只报告；已经授权修复的工作在原范围内处理，不增加重复确认。新的取舍或超范围变更另行确认。
- 有缺口时由现有 TOP 任务承接；复核只覆盖发生变化的项，不无上限“实现—再找事—再实现”。没有新证据时说明限制并停止，不给“绝对完美”的保证。

## 验证边界

- 单测通过但配额错误仍在真实界面显示“处理中”：属于实际行为与要求冲突，不能用单测数量冲抵。
- 只读分析未发现问题但服务未启动：不能报告线上验收通过。
- 已批准的需求变化使旧验收过时：核对最新决定并更新原真源，不同时维持两套互相冲突的判据。
- 明确改一个文案：走普通审查，不触发全功能需求扫描。
