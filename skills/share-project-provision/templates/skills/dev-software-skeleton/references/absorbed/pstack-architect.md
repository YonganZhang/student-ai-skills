# 软件骨架设计流程

来源：cursor/plugins 的 pstack architect、how、arena 与 architect references；固定版本见随包 UPSTREAM.json。MIT，Copyright (c) 2026 Lauren Tan。本地语义适配。

## 触发与输入

显式：设计软件骨架、设计架构骨架、搭建软件骨架、开启骨架模式、开启 Potato 模式。自动：当前任务需要确定软件的模块边界、状态归属、核心数据模型或跨模块接口；普通接口实现、局部修复、论文框架与方法绘图不因此触发。

从业务目标、调用者使用场景、规模、现有代码和运行约束提取输入。能查代码或实验确认的问题先取证；产品取舍缺信息时才问。设计范围由任务决定，不预设后端或微服务。

## 流程与完成条件

1. **理解现状**：读取项目入口与受影响模块，追踪输入到输出、持久化和状态写入者；记录现有设计依据与不可破坏的约束。全新项目则记录已知需求和假设。完成时，每个受影响边界都有代码证据或明确假设。
2. **调用者优先**：先写 2–3 个真实使用场景，再推导类型、签名与模块关系。说明状态唯一所有者、边界校验、错误和重试语义。完成时，场景能由接口表达且不需要调用者协调内部步骤。
3. **比较方案**：提出至少两个结构有实质差异的候选；按业务覆盖、接口复杂度、数据一致性、改动成本与可验证性比较。若约束只容许一种结构，写清排除另一方案的证据。主代理可串行比较；仅在宿主规则允许且任务确需独立探索时委派，不固定模型或强制调用外部模型。
4. **筛选与综合**：检查空转封装、内部表示泄漏、多处写同一状态、手工同步清单及双实现路径。选择一个基础方案，说明吸收其他方案的哪些部分与原因，不机械拼接。
5. **交付骨架**：按规模给出模块图、数据模型、关键接口或类型草图、目录建议、设计理由、未决项及第一条实现切片。草图中的占位实现须明确标识，不宣称可运行。遵循项目已有文档位置；方法关系需要图时调用 content-technical-roadmap，进度沿用 project-top，不另建一套计划。
6. **验证与回看**：用正常、失败、重试场景走查数据与责任边界；若输出了代码则做适当编译/类型检查。只设计时不虚称业务测试通过。实现持续出现相同绕行或状态冲突时回到现状与方案阶段，修正骨架。

## 交付说明

说明解决的问题、推荐结构、输入输出、候选取舍、已验证内容和下一步。只要求设计就止于可审阅设计；已授权实现则沿骨架推进，不追加例行确认。涉及部署、数据或其他外部动作时遵守当前会话授权。

## 与上游的差异

保留先理解、调用者优先、数据结构优先、多方案比较和真实验证；将 how/arena 所需方法内联适配，避免安装缺失的 Cursor 技能依赖。未吸收整个 pstack、固定模型、强制并发、自动外发或上线权限。移除 disable-model-invocation，以支持用户要求的中文自然语言与任务自动触发。
