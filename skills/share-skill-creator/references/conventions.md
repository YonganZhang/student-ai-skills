# 规则与技能写法

## 强制：指针 + References 模式（适用于 Rule 和 Skill）

**核心原则：约束完整、任务效果优先；常驻精简，详情按需。** 长度是维护提示，不能作为删除必要约束、触发语义或流程的理由。 每个 prompt 常驻加载的只应该包含"要做什么 + 关键值 + 指针"，具体命令/流程/代码细节挂到 skill references 里，触发场景出现时才 Read。

### 全局规则写法

全局规则只保留每轮确实需要的偏好、授权边界和工作原则。新增一句前，先判断它会改变什么实际行为。

- 一个要求只保留一处。通用原则放全局，按任务触发的方法放技能，项目约定留在项目里。
- 直接写条件与动作；用通用词表达，不加“用户定”、日期、事故叙述、平台使用者名单或自我解释。
- 命令、工具参数、机器配置和案例由所属文档维护，规则只给必要入口。
- 能从当前配置或实际结果查到的状态，不抄成常驻文字；能由工具检查的约束，交给工具。
- 只有真实问题或明确偏好才形成约束；先修已知来源，再判断是否需要规则。
- 删除无效或过宽的要求，合并重复要求；不要为保留字数而把它们整段搬进 references。
- 以是否清楚、适用和可执行为准，不用行数或禁令数量代替判断。授权边界保持清楚，按已授权范围直接完成修改。

### Skill description 是 router prompt，不是给人读的

`description` 给 Claude/Codex 在读取正文前判断是否使用技能。优化目标同时兼顾三件事：
- **召回率**：覆盖真实需求的关键说法；按用户用语保留中文、英文术语或别名，不机械重复翻译。关键词不能保证必然召回。
- **精准度**：没需求不命中 → 边界清晰，易混淆场景显式声明"不触发：XX"
- **字数最小**：摘要通常进入技能发现上下文，删除无用词；实际 token 与缓存成本以宿主用量为准。

**标准格式**：`"一句话定位（类别 + 核心关键词）。触发：少量代表性用户说法。不触发：易混淆场景（可选）。"`

**编辑目标**：description 通常 ≤140 字符（中文一字算 1，用 `len()` 计），“做什么 + 关键触发词”放最前，“不触发”边界压成末尾一小句。这是本地编辑目标，不是平台技术限制；必要语义无法在此范围内表达时可超出，保留内容并验证选取效果。宿主展示和截断行为以当前会话实测为准；修改后核对关键用途与边界在实际技能清单中完整可见，不能只靠字符计数证明路由有效。

**多子技能 description 规则**：
- 子技能 ≤2：父 description 可轮廓性提到子能力，但不列完整触发词。
- 子技能 >2：父 description 写成"能力类别/模式"，语义笼盖所有子能力，不逐项展开。
- 示例：Office 主 skill 写"Office 文档操作，覆盖 Word/PPT/Excel/PDF/图片转文档等"，不要写每个 Word/PPT/Excel 子命令。
- 子技能自己的详细触发时机写在父 `SKILL.md` 的路由表或对应 `references/`，不放父 description。

**反面例子**：`"科学论文撰写技能 — SCI 论文写作、文献综述、引用管理、同行评审、博士论文、基金申请书。"`（类别罗列式，无触发词，"引用"歧义大会误触代码引用）

**正面例子**：`"写 SCI 论文 / 文献综述 / 基金申请书 / 博士论文。触发词：写论文、撰写论文、写基金、开题报告、审稿意见回复、PhD thesis。不触发：代码函数引用、代码审查（走 review）。"`

### 对 Skill（个人技能在 `~/.claude/skills/`（Claude Code）、`~/.agents/skills/`（Codex），项目技能在 `.claude/skills/`、`.agents/skills/`；两端共用时可软链到同一份；触发时加载）

**SKILL.md 是目录，不是文档。** 所有新建 skill 默认采用此结构，触发加载时才省 token：

```
my-skill/
├── SKILL.md              # 索引，目标 ≤80 行：触发词 + 场景映射表 + 指向 references 的一行引用
├── references/
│   ├── detail-a.md       # 细分场景/深度内容（Claude 按需 Read）
│   └── detail-b.md
├── scripts/              # 确定且重复的动作才脚本化
└── assets/               # 模板 / 输出资源
```

SKILL.md 里用 `详见 references/detail-a.md` 或 `执行 scripts/foo.py` 指路，不要内联细节。

**拆分检查点：**
- SKILL.md > 500 行 → 优先评估拆分；150–500 行 → 检查只在部分场景用到的内容能否下沉 references。reference 按职责、读取成本和可导航性组织，不为行数切断一个完整流程；长文补目录。
- 命令示例可内联；确定且重复的逻辑抽脚本，不为行数制造没有消费者的工具
- 某一场景逻辑 > 30 行 → 检查是否适合抽到 references；共性合同和执行前必知条件留在入口。
- 独立子能力 > 2 个 → 优先采用 router/book；迁移前确认父 description 能召回该类请求，入口有明确读取条件与有效路径，再用真实正例和相邻负例核验。
- 独立子能力 ≤ 2 个 → 顶层可保留主流程，只加路径指针和"何时读"说明
- **Rule > 60 行** → 必须评估拆分；命令、案例和长流程优先挂到 skill references

**例外：** 极短工具型 skill（<50 行）可单文件，但仍避免内联长代码。

## 命名与可见性

目录名用小写字母加连字符，入口文件必须是大写 `SKILL.md`。目录名与 frontmatter `name` 最好一致；本包部分目录为兼容保留旧名（如 `share-skill-creator` 目录的 `name` 是 `agent-skill-creator`）。同一宿主里 `name` 不能重复。只经父技能路由的子流程用 `REFERENCE.md` 或普通 reference，不命名 `SKILL.md`，避免被当成独立技能曝光；不要为隐藏摘要删掉正文或授权边界。

## Rule + Skill 联动

当需求同时涉及"每次都要遵守"和"详细参考内容"时：

- **Rule / 常驻说明**（Claude Code 的 `CLAUDE.md`、`.claude/rules/*.md`，Codex 的 `AGENTS.md`，常驻最小）：触发条件 + 短边界 + 指向 Skill
- **Skill**（按需加载）：完整详细规则 + references

示例：项目 `AGENTS.md` 写一行“提 PR 前用 dev-pr-self-check 自检”，完整流程与脚本在 `dev-pr-self-check` 技能里。

创建 Rule 时始终评估是否需要配套 Skill。

## 升级既有 skill 的流程

1. 盘点 SKILL.md 章节，标出独立场景
2. 每个独立场景拆到 `references/<场景名>.md`
3. SKILL.md 保留：触发词 / 场景表 / 共性约束 / 到 references 的一行链接
4. 验证：核对仍有效的约束、授权边界和执行时机，撤掉过宽或已失效的要求；检查真实请求能选中且读到对应流程，再实测上下文变化。约 150 行仅为入口目标，不预设必须下降的 token 比例。

重构优先级按实时审计结果和触发频率决定：先处理运行时可见、超过 150 行且高频触发的入口，不在规范里维护会过期的排行榜。

## 杜绝死代码（写脚本前的自检）

**每次在 `skills/<name>/scripts/` 新建任何脚本前，必须先回答三问**：

1. **SKILL.md 或 references 里能否加上对这个脚本的引用？** 如果不能（写了也没人读），就别写这个脚本。
2. **是不是新版本？** 如果是 `v6/v7/v8` 这种迭代，旧版必须同时移入 `scripts/_archive/` 或删除，不保留在 scripts/ 根目录里误导后续读取。
3. **是不是一次性 demo/调试脚本？** 如果是，放桌面或项目里，不放进 skill scripts/。Skill scripts/ 只存"未来还会被多次调用"的工具。

**落地机制**：技能涉及脚本新增、移动或调用变化时，对受影响目录运行 `scripts/scan_orphans.py`，再检查 import、测试及外部消费者；扫描命中只是候选。已授权范围内补引用或修复调用；确认无消费者后删除或移入 `scripts/_archive/`。只有归属、保留价值或处置授权未明确时才向用户询问，不因误报中断工作。

**反例**：某个生图脚本里定义了 142 行 `SYSTEM_PROMPT` 常量从未被使用，实际发给模型的是另一段 `full_prompt`——典型"写完没挂上调用链"的死代码。
