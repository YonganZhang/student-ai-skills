# 从用户纠正到可复用 SOP

当用户要求把做事方法变成规范，例如“以后都这样、不要再逐处补、变成 SOP”时，用本流程把案例转成文件系统真源。若只是记住事实、个人偏好或历史决定，写进宿主的记忆功能或项目说明（`CLAUDE.md`、`AGENTS.md`）即可；项目当前进度走 `share-top`。本流程负责可检查、可同步、可回滚的 rule / skill / reference / script，不将普通事实写成规则。

## 目标形状

一条合格的沉淀应回答四件事：

- **条件**：什么意图或环境出现时生效。
- **不变量**：无论具体案例如何变化，都必须保持什么。
- **边界**：哪些相邻场景不适用，应该交给谁。
- **验证**：怎样证明它能触发、不会误触，并真的改变执行。

具体人名、日期、文件名和一次性事故只作为证据或测试，不充当规则主体。

## 内容分层（写进 skill 之前先分类）

skill 正文只放**类层规则**：换一篇论文、一个项目仍然成立的做法，写成“条件 → 做法 → 为什么 → 边界”。其余内容按下表落位：

| 内容 | 判别问题 | 落点 |
|---|---|---|
| 类层规则 | 换一篇论文/一个项目还成立吗？ | skill 正文（SKILL.md 或它路由到的 reference） |
| 领域包 | 只在某个领域成立，但对该领域任意论文/项目都成立（术语、惯例、评估规范） | `references/domains/<领域>/` 之类的按需加载目录；写成领域规则，不写单篇参数 |
| 示例 | 说明某条规则的具体句子、段落、图或命令 | 紧跟它说明的规则，标“示例”，可替换，每条规则至多 2 个；长范文放 `examples/`。规则本身不能只存在于示例里 |
| 单篇 / 单项目约定 | 只对一篇论文、一个项目、一个数据集成立（阈值、样本数、图号、指定措辞、路径） | 该项目的 AGENTS.md / `_wiki` / TOP，skill 里不留 |
| 历史与来由 | “某日用户拍板”“之前犯错”“从某次投稿沉淀” | changelog / 吸收日志；规则正文只保留 why |
| 伪规范 | 没有来源的目标值（“R² 控制在 X–Y”）、让结果“看起来”更好的技巧 | 删除，改成判断标准或排查步骤 |

枚举清单超过约 7 项又没有组织原则时，先提炼原则，再保留少数代表例。

**适用时机**：新建 skill、吸收外部 skill、按某篇论文或某次对话的反馈修改 skill，三种情况都要过这一步，不只在用户说“记住”时。检查：逐个文件读一遍，找显性的项目名、人名、事故叙事和无来源目标值，可用 `grep -rnE '<项目名>|<人名>|用户(批评|拍板)|之前犯错|控制在 *[0-9.]+ *[-–~至到]' <skill 目录>` 辅助；命中是候选，标注清楚的示例可以保留；“清单式枚举”仍要人读判断。

## SOP

### 1. 捕获意图，不抄原话

从当前对话提取用户真正要长期改变的行为。区分一次性交付、项目约定、全局偏好和安全边界；不确定且会改变范围时才询问。

### 2. 升到类层

检查同类问题和现有真源。用一句话写出根因类别，再形成“条件—不变量—边界—验证”。显式用户偏好和安全边界可以单次沉淀；一般抽象仍遵循 Rule of Three。

### 3. 选择唯一落点

| 内容性质 | 真源 |
|---|---|
| 每轮都必须知道的短边界 | 全局或项目 rule |
| 需要按意图触发的工作方法 | skill router / workflow |
| 长知识、案例、故障树 | reference |
| 重复且确定的机械动作 | script，并从 skill 挂载 |
| 单项目路径、数据、约定 | 项目级 rule / skill / TOP |
| 历史原因和版本变化 | changelog / audit history |

吸收外部能力或决定 skill 范围时，先按 [全局 / 项目 / 可选模块](placement-and-modules.md) 选择。可选模块不全局曝光，启用后成为固定版本的项目技能。

同一事实只保留一个权威落点；其他位置使用指针，不手写镜像。

### 4. 合并而不是追加

先搜索同义规则、旧入口、相邻技能和反向约束。优先修改已有章节；若新原则取代旧原则，同时删除、归档或加 tombstone，避免新旧同时触发。

### 5. 写成接口，不写枚举

- description 只表达能力、代表性触发和相邻边界。
- 主 `SKILL.md` 写决策和路由，不堆案例清单。
- 将案例改写成正向测试或 near-miss 负向测试。
- 解释关键 why，让模型能处理未枚举的新变体。

### 6. 双边语义吸收

同时适用于 Claude/Codex 时，先固定共享不变量，再分别适配路径、工具、hooks 和 loader。按 `accept / adapt / reject-with-reason` 记录差异；不复制 auth、session、MCP live env 或本机凭证。

### 7. 验证闭环

至少验证：

1. 一个用户真实说法能触发正确 skill。
2. 一个相邻 near-miss 不会误触。
3. 所有引用存在，脚本有调用入口。
4. 旧冲突入口已删除、归档或明确分流。
5. Git diff 只含目标真源，敏感文件被忽略。

客观且高风险的能力再跑完整 eval；纯路由/规范更新可用静态审计和代表性触发测试。

## 失败时如何修

- **没触发**：先改 description 的意图表达，不向正文堆更多触发词。
- **误触**：补相邻边界和 near-miss 测试，不增加多层 if/else。
- **执行仍错**：修 workflow、不变量或工具接口；不要继续改路由掩盖病因。
- **双边漂移**：先判断是平台适配还是语义缺失；只有共享不变量要求字节一致。
- **总在重复人工步骤**：确认稳定后脚本化，并保留可观测输出和失败状态。

## 完成判据

只有当真源唯一、入口能触发、相邻场景能分流、旧冲突已处理、验证通过且双边完成语义验收时，才算“记住了”。
