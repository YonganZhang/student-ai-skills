# Skill 叉树结构原则（渐进式披露）

## 核心理念

skill 是"按需加载"的知识树，不是"一次性灌输"的长文档。

```
SKILL.md (一级)              ← 启动只展示 name/description；选中后读正文
  │ 极精简：触发词 + 核心 3-5 条原则 + 二级跳转索引
  │ 目标：~150 行（超出要有理由，500 行本地拆分检查点），router 通常 ≤80 行；看完能完成路由和 80% 常见判断
  ↓
references/<topic>.md (二级)  ← 触发后 cc 才读
  │ 中等：某个子主题完整内容 + 可选三级跳转
  │ 目标：< 3K chars，每个文件聚焦一件事
  ↓
references/<topic>/<sub>.md (三级，可选)  ← 二级文档引用才读
  │ 详细：边界 case / 历史踩坑 / 命令大全
  │ 目标：< 5K chars，最深一层
```

## 为什么这样

- **token 经济**：常驻候选清单只含 name/description；选中技能后才读一级正文，再按需读二三级资料
- **认知友好**：用户/AI 先看核心，需要细节才往下挖，不被信息淹没
- **可维护**：改一个细节不动一级文档（高频被加载的）

## 反模式（要避免）

- ❌ SKILL.md 几万字符把所有内容塞一起（如某写作技能入口曾达 19K 字符）
- ❌ 一级有完整命令 + 完整故障排查 + 历史踩坑 + 边界 case（一级只放索引）
- ❌ references/ 平铺 30 个小文件没层级（要分主题分组）

## 检查 checklist

新建 skill / 改 skill 前问自己：
1. SKILL.md 是否在 ~150 行左右（超过 500 行检查拆分或补目录，完整流程优先），且没有只在部分场景才用的、可下沉的手册细节？
2. 80% 用例只看 SKILL.md 就够？
3. 每个 reference 是否聚焦一个完整主题、路径可发现，长文有目录或可定位章节？3K/5K chars 只是读取成本提示，不是删内容的阈值。
4. 一级是否包含三级才该有的细节？

## 例子（主题目录示意）

```
my-ops-skill/references/<topic>/
├── REFERENCE.md                                  (按需读取的主题入口)
│   ├── 触发词
│   ├── 核心 3 条原则
│   ├── 症状识别表（4 行）
│   └── 二级跳转 N 个
└── references/
    ├── setup.md
    ├── operations.md
    ├── troubleshooting.md
    └── verification.md
```

主题资料保留完整内容，经父入口按需读取；常驻成本以宿主实际候选清单与上下文测量为准。

## 适用范围

- 较长 skill（如 >3K chars）检查是否适合分级；完整流程、必要语义与可导航性优先
- 小 skill（<2K chars）可以单 SKILL.md，不强求拆
- 极简 skill（<500 chars）一级足够，不需要 references

## 按分支下沉与后续扩展

当多个常见任务共用一个入口，而恢复、迁移、特定提供方或某类安装只在少数任务需要时，入口保留共用边界和任务路由，完整分支合同放到对应 reference。读取条件写到路由旁；不能为了精简把公共授权、身份和数据边界藏到偶发分支。

新增内容先找已有所有者与模块，只在对应模块加一条路由并把细节放目标文件；新建独立类别才调整主入口。下沉时修正相对路径、旧章节指针和完成标准；保留脚本消费者，不复制第二份规则。验证常见任务不必读低频分支、目标任务仍能到达完整合同；记录实际入口读取量，不把行数下降当成模型效果证明。

## 何时该是顶层 skill / 何时该是别人的子 reference

新建 skill 前问自己：

```
这个 skill 的"主语 / 主场景"是什么？
  ↓
这个场景在"主语"之外还有用吗？
  ├─ 有 → 独立顶层 skill 合理（如跨项目的网页操作与验收）
  └─ 没有 → 应该是"主语 skill"的 reference，不要独立顶层
```

**反例**（曾经犯的错）：
- ❌ 把一次性迁移说明做成顶层 skill — 平时不会独立触发
- ✅ 应该归入对应主 skill 的 `references/` 或全局 `_legacy/`

**正例**：
- ✅ `playwright-cli` 顶层 — 多种项目都会请求网页操作与验收
- ✅ 服务器加固归入运维总技能 — 父描述覆盖该类请求，路由明确指向 `references/server-hardening/REFERENCE.md`；缺少任一项就不能只为减少入口而迁移
- ✅ `permissions-setup.md` 是具体工具的 reference — 只在安装或修复权限时按需读取

## token 经济账

技能名称与 description 在技能选择前可见，本地编辑目标约为 140 chars，必要语义优先；实际发现范围和固定上下文开销以当前宿主会话测量为准。
作为 reference 的文档经入口路由按需读取，父技能必须明确何时读取。

减少重复候选可能降低固定上下文开销；同时测父描述长度、实际读取量和真实任务效果，不预设字符到 token 的固定换算或必然收益。

## 主技能 / 子技能阈值

- 子能力 ≤2：主技能可以仍是正常工作流；在相关步骤放一行指针，例如"涉及 X 时读 references/x.md"。
- 子能力 >2：主技能改成目录型 router；一级只保留类别边界、共性规则、子能力路由表。
- 子技能默认是 `references/` 里的普通文档，不命名 `SKILL.md`；只有用户会直接点名、且脱离父技能也有独立主场景时，才允许嵌套 `SKILL.md`。
- 父 description 表达能力类别与关键边界；必须覆盖子能力的独立请求，不为缩短描述牺牲召回。

例：Office 主技能 description 写"Office 文档操作，覆盖 Word/PPT/Excel/PDF/图片转文档等"；Word 修订、PPT 生成、Excel 清洗的细节在父 `SKILL.md` 路由表里指向各自 reference。
