# 需求、任务与验收证据的关联

## 范围与真源

对已有复杂功能 spec，在开工前与交付前各按需要做一次覆盖核对。只看本次约定范围；明确小修改继续使用原任务与验收，不新增表格或流程。

- 需求与验收定义留在项目 spec 真源，写法见 [需求质量检查](../../../grill-to-spec/references/absorbed/spec-kit-requirements-quality.md)。
- 当前任务状态仍只在 `_task_plan.md`；证据仍归 Tests / 项目既有证据入口。
- 映射只存稳定引用。优先使用既有 traceability 表；没有时，在现有任务描述中写明 `spec路径#要求编号`，使用项目当前支持的 `scope` / `gate`。不增加自定义解析字段，不创建另一份 `tasks.md`。
- 一项要求可以对应多个任务，一项任务也可支持多个要求；基础设施任务可关联已接受的技术约束或使能依赖，不必伪造用户故事。

## 开工前

1. 从已确认 spec 提取本次可交付要求及相关验收，复用已有引用；不把远期业务效果当作开发任务完成条件。
2. 用现有 CLI 读取任务与 scope/gate，检查每项要求是否有负责的任务和适当的验收安排。
3. 反向检查任务是否能追溯到要求、已接受约束或必要依赖。缺少关联先核对，不能直接断言任务无用。
4. 漏项若已在用户批准的工作范围内，用 `sixone-cli.py plan add|edit` 补到现有任务。范围之外的建议单列，不自动扩大计划。

## 交付前

按 [需求收尾核对](../../../share-code-review/references/absorbed/spec-kit-convergence.md) 检查当前实现，并把结果与真实验收证据关联。

需要展示时，在回复或项目现有审查记录中生成一次有日期、范围与代码版本/运行标识的快照：

| 需求引用 | 任务引用 | 验收入口 / 证据引用 | 本次核对结果 |
|---|---|---|---|
| spec路径#R1 | 现有任务编号 | 测试入口及匹配本次实现的结果 | 已验证 / 有缺口 / 未验证 |

该表是核对记录，不是第二份实时任务台账；不复制需求正文，不持续手工同步状态。旧结果只有能证明仍适用于当前相关实现、环境和输入时才可复用；否则列“未验证”。测试入口存在或任务打勾不等于验收通过。

## 修复与停止

先匹配已有任务：缺口属于未完成任务就编辑该任务，属于曾完成任务则按现有 CLI 重开；无对应项且仍在授权范围内才新增，避免每轮追加同义任务。任务变化仍走已有计划验证与收尾流程。

默认只做一次有边界检查，报告重要缺口和未验证部分；相关实现或证据变化后才复核受影响项。不循环生成文档，不靠提高“关联覆盖率”宣称产品可用。

## 验证边界

- 需求有任务但没有有效测试结果：关联存在，交付仍是“未验证”。
- 测试全绿但取消行为无对应要求或检查：不能把取消行为算已验收；先确认它是否在约定范围内。
- 合法共享基础设施有设计依据：保留其关联，不按“没有用户故事”误删。
