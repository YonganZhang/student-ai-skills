# 能力清单（Capability Inventory）

## 要解决的失败模式

AI 报「缺数据 / 做不了 / 没有条件」，而项目本身拥有能产出该资源的东西。
真实约束是**成本**（时间、算力、配额），却被报成**能力边界**，于是：

- 用户以为路走不通，据此改方向
- 或者 AI 绕道去做次优方案，浪费的比直接生成还多

根因：六合一原本只登记「**已经有什么**」（COL4 代码、COL5 数据资产），
没有一栏登记「**能造出什么**」。已有资产是名词，能力是动词，两者不能互相替代。

## 判据（这是通用规范，不是某个项目的清单）

### 什么算能力

能**按需产出主线所需资源**的东西。跨项目类型举例：

| 项目类型 | 典型能力 |
|---|---|
| 科研/仿真 | 模拟器、实验台、可复跑的采集流程、标注流程、算力配额 |
| 软件开发 | 可重建的测试环境、种子数据生成器、可复现构建、CI、回放录制 |
| 数据/分析 | ETL 管线、抓取器、API 配额与密钥、数据订阅 |
| 内容/文档 | 可复跑的渲染流水线、素材库授权、批量转换工具 |

### 🔴 收录判据（防止 AI 把所有东西都写进去）

一个东西进能力清单，**当且仅当**：

> 主线任务里存在一个「**如果没有它，就要说做不了**」的问题，而它能解决。

推论：
- 通用工具链（编译器、编辑器、常见库）**不进** —— 它们不解决"做不了"
- 装了但主线用不上的**不进**
- 主线换了，清单要跟着删 —— **它不是装机清单，是主线依赖清单**

### 每条必须写全三项

| 字段 | 为什么必须 |
|---|---|
| **能产出什么** | 没有它就无法判断能否解决当下的"缺" |
| **单位成本** | 把"做不了"翻译成"要多久/多少算力"的依据 |
| **当前是否可用** | 环境失效的能力等于没有；不写会造成第二次误判 |

## 不变量

> **说「缺 X / 做不了 / 没有条件」之前，先对照能力清单。**
> 若清单中有能产出 X 的能力，则如实报告为**成本问题**
> （「需要 N 小时 / N 核时」），不得报告为能力边界。

## 边界

- 能力清单**不替代** COL5 数据资产登记。资产是已产出的实例，能力是产出手段。
- 能力清单**不承诺**结果质量。「能生成」不等于「生成的能用」，
  质量仍由 COL3 的 gate 判定。
- 成本估计必须基于**实测**单位成本，不得凭印象。没实测过就标注 uncertain。

## 验证

项目 doctor 时可检查：
1. 清单每条是否三项齐全（产出 / 成本 / 可用性）
2. 是否存在**主线依赖但未登记**的能力 —— 反查方式：
   在计划与发现文档里搜「做不了 / 缺 / 没有条件 / 无法」，
   逐条确认是真边界还是未登记的能力
3. 主线变更后，清单是否仍与新主线对应（旧主线专属能力应移除）
