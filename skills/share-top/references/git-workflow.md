# Git 操作与追踪细则

Git 是每个项目的版本骨架：代码、文字和项目记录靠它留历史、能回退、能追到"为什么这么改"。本规则回答五件事：怎么保护别人的改动、什么该进 Git、什么时候由谁提交、乱了的仓库怎么收拾、推送与 worktree 的边界。

## 保护工作区

- 不回退、覆盖或清理自己没创建的改动。不运行 `reset --hard`、`checkout --`、`restore`、`clean -fd` 等破坏性命令，除非用户点名；不为隔离别的会话预先 stash（`stash pop` 可能静默留下冲突 marker）。
- 按具体路径 `git add`，不盲目 `add -A`：共享仓库里可能有别的会话做到一半的改动。提交前看 `git status --short`，提交信息基于实际 diff。
- 只提交自己这轮产生的文件；项目共有的 TOP 记录例外（见"什么时候提交、谁提交"）。

## 什么进 Git：看文件是怎么来的，不看有没有价值

判断发生在写文件的当下。那时往往还不知道它有没有用，价值要事后才看得出；如果拿"有价值"当追踪门槛，等看出价值时，没追踪的东西可能已经丢了或被覆盖。所以按来源判断：

| 类别 | 判别 | 处理 | 示例 |
|---|---|---|---|
| 写出来的 | 人或 AI 逐字写出的文本 | **一律追踪**，包括沙盒里的试验代码 | 代码、绘图脚本、配置、论文源文件、TOP 记录（计划、日志、finding、决策） |
| 小而难重新生成的结果 | 是生成的，但体积小，丢了要花大代价重做或再也拿不到 | 追踪 | 指标汇总表、论文终稿图、手工标注、外部来源可能消失的小数据 |
| 能重新算出来的产物 | 由已追踪的代码 + 配置 + 数据跑出来 | **不追踪**，改为追踪它的配方；数据位置与哈希登记到 data registry | 逐样本输出、模型权重、中间结果、`_tmp/`、测试截图和录像 |
| 环境与缓存 | 由包管理器或工具生成 | 永不追踪 | 虚拟环境、`node_modules`、各语言包缓存、`__pycache__`、索引缓存 |
| 凭证 | key、token、私钥、`.env` | 永不追踪；已进历史的按"大文件、凭证与公开仓库"处理 | — |

- 拿不准时问一句："删掉它，能不能用仓库里已有的东西一条命令重新生成？"能 → 不追踪，但确认配方已追踪；不能 → 追踪，太大就登记位置和哈希。
- "追踪配方"的意思：生成物不进 Git，但产生它的脚本、配置、参数、随机种子和输入数据版本必须能在 Git 或登记里找到。找不到配方的结果无法复现，也就不能当证据。
- 大小是信号不是规则：单个生成文件超过约 10MB 默认不进 Git（全局 pre-commit 在 50MB 硬拦）；写出来的文本超过约 1MB 时看一眼它是不是其实是生成的。

## 进 Git 不等于转正式

- 进不进 Git 按上面的来源规则；转不转正式看它有没有推动计划：沙盒代码进 Git 但不接正式流程，有证据推动计划后才晋级、登记并在 `plan complete` 证据里引用。失败的实验也推动计划——结论写成 finding 追踪，代码留沙盒或归档到 `_legacy/`，不删历史。晋级、退役与归档细节见 share-top `references/git-version-lifecycle.md`。
- 不用版本号复制代码：不建 `v2/`、`model_v3.py`、`_final`、`_backup` 这类副本（目录和文件都不行）。版本就是 Git 提交和 tag；副本会让 import 与引用全要跟着改，还会改一处漏一处。实验隔离用 `_sandbox/<日期>-<主题>/`；运行结果可按运行建子目录，便于并排比较。
- 科研项目与开发项目用同一套来源判断，差别只在 `.gitignore` 默认值（share-top `templates/gitignore/`，初始化项目时按类型写入）：科研项目追踪汇总层（表格、指标、终稿图、finding）、忽略批量层；开发项目忽略构建产物、测试截图录像、覆盖率与依赖缓存，追踪测试夹具和少量种子数据。

## 什么时候提交、谁提交

- 持久授权（用户 2026-09-23）：验证过的改动就在**所在工作树的分支本地提交**。
- 推送授权示例：用户若授权“**归档**完成后推送”，把当前分支推送到**私有**远端——先用 `gh repo view --json visibility` 确认是 PRIVATE；公开仓库、没有远端、需要 force 或远端领先时不推，报告给用户。其余 push、改写历史仍需用户同意；工作树按下节的持续授权执行。
- TOP 项目用 `plan complete <项目> <ID> --evidence … --commit`：它把任务 scope 和证据里的文件、计划、日志以及整个 TOP 目录（finding、决策等项目记录）合成一个提交。
- TOP 记录属于项目、不属于某个窗口：谁做计划提交，谁就把 TOP 目录下的改动一起带上，不必等写它的那个会话。
- 及时提交，不要攒：未提交的内容不在历史里，换窗口、换模型或误操作后可能找不回。一个阶段的逻辑改动验证完就形成提交。
- `plan complete` 报告 scope 外还有"写出来的"文件没进 Git 时，补进任务 scope 或单独提交；报告有生成物没被忽略时，按下一节加忽略规则。
- 多个窗口共用一个仓库时，各自只提交自己的文件；需要隔离时按 Worktree 一节创建或复用任务工作树。
- 重要验证或实验先绑定实际内容（TOP 项目用 `sixone version`）；HEAD 或 tag 不代表未提交内容。

## 整理已经乱了的仓库

- 先跑 `python3 ~/.claude/skills/share-top/scripts/sixone-cli.py track <repo>` 分拣"该提交 / 该忽略 / 需判断"（只报告，加 `--write-gitignore` 才写忽略规则，从不自动提交或删除）；误提交的缓存 `git rm -r --cached <目录>` 并加忽略、文件留盘；要从历史彻底清掉（大文件、凭证）属于改写历史，先问用户。细节见 share-top `references/git-version-lifecycle.md`。
- 有窗口正在该仓库工作时，把清单交给那个窗口自己收尾。首次建仓先写 `.gitignore`（share-top 模板）再做第一次提交。

## 大文件、凭证与公开仓库

- 全局 git hooks（share-top 的 `git-hooks/`）在提交时拦下超过 50MB 的文件和像真凭证的字符串。确认无误才用 `TOP_ALLOW_LARGE=1` / `TOP_ALLOW_SECRETS=1` 单次放行，不要为了过检查而绕开检查。
- 凭证已经进了历史：先到服务商作废或更换，再改成从环境变量读取，最后清历史（需用户同意）。只在当前版本删掉不算处理完。
- 项目仓库默认建成私有；改成公开要用户明确同意。公开仓库设 `git config top.sessionTrailer false`（会话号不外发）。

## 远端与推送

- 不 force push 主分支；改写过的分支推送用 `--force-with-lease`。
- 远端或 git/gh 的权限、scope、TLS 异常，先查 `gh auth status`、remote、branch、fetch 并报告，让用户定策略。
- 推送前看 `git status --short --branch`，跑与改动匹配的最小检查（文档查链接、UI/API 看行为证据、构建/依赖跑 smoke）；CI 没跑不写成通过。

## Worktree

- 长任务已有创建授权：预计多轮或数小时、涉及多个文件的持续开发，或同项目已有其他窗口修改时，使用一个独立任务工作树；几分钟的小改留在当前工作树。
- 一个窗口同一时间使用一个任务工作树，子智能体在其中按互不重叠的文件分工。先复用当前任务工作树；需要新建时放 `~/projects/_worktrees/<项目>-<任务>`，分支用 `task/<任务>`。项目已有管理目录时沿用它。
- 创建前核对主工作树的未提交改动、ahead/behind、已有工作树和任务依赖。依赖尚未提交的修改时先与其所有者协调，不从旧 HEAD 开工，也不 stash/reset 别人的改动。
- 谁开谁收：完成且验证通过后合回主分支，再删除本任务工作树；冲突由本任务解决并重新验证。未完成就提交到任务分支，在 TOP 留交接。
- 一个项目超过 3 个工作树时列清单提醒；已合并、干净且确认没有窗口或进程使用的可清理。未合并或仍使用中的只列出状态，不代替其他窗口合并半成品。
- 发布通过 `git archive <提交>` 导出普通目录，不为每次发布创建工作树。
- 人话总结报告实际工作树名与分支；主工作树明确标注“主工作树”，不在 Git 仓库时报告文件夹名。
