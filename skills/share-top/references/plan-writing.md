# 计划怎么写：目录格式与写法

> 2026-10-16 起新计划默认用**问答格式**（[qa-plan.md](qa-plan.md)）：一个项目是一串问题，人读问题和答案，AI 在每个问题的工作本里记尝试；短碎任务不进计划。本文件说的是旧的**目录格式**（阶段 → 步骤），这样的计划照常能读能写，改写成问答格式见 qa-plan.md「迁移」。

计划是写给人看的。用户打开计划看板或计划文件，30 秒内要看懂四件事：**要做成什么、现在在第几步、下一步做什么、卡在哪**，并且能顺着各阶段读出整个项目的来龙去脉。AI 每轮收到的提示也只有这四件事。所以计划写成一份目录（planning-with-files 的 `task_plan.md` 套路），不写成日记、证据清单或实验台账。

## 三层内容，各放各的地方

| 层 | 放什么 | 写给谁 |
|---|---|---|
| **标题**（阶段名、步骤） | 逻辑层的一句人话：这一段/这一步要回答什么、得到了什么；可以抽象，但要紧扣主线 | 不懂技术细节的人也要一眼看懂 |
| **阶段小结**（每个阶段一两句） | 承上启下：为什么做这一段、得到了什么、所以接下来做什么；可以带一两个关键技术点 | 想了解来龙去脉的人 |
| **细节文章** `_wiki-methodology/_top/_plan_details.md` | 技术细节：数字、实验编号、方法名、文件路径、证据、旧编号对照；按阶段分节，和计划目录一一对应 | 追问细节的人，以及需要细节才能动手的 AI |

碎片化的细节不进计划。用户想知道时会问，AI 回答时去细节文章、findings 和日志里查。AI 平时读计划也只需要主线。

## 形状

```markdown
# <项目> — 计划

## 目标
<一两句人话：整件事做完是什么样>

## 现在
<!-- plan 命令自动生成，不要手改 -->
- 阶段：第 2/4 阶段 · P2 <阶段名>
- 正在做：P2.2 <步骤>
- 下一步：P2.3 <步骤>
- 卡点：无

## 各阶段

### P1 <阶段名> ✅
<一两句小结：得到了什么，所以下一阶段做什么>

- [x] P1.1 <做了什么：结果怎样> <!-- ev=… -->
- [x] P1.2 <做了什么：结果怎样> <!-- ev=… -->

### P2 <阶段名> 🔄
<一两句小结：为什么做这一阶段，现在到哪>

- [x] P2.1 <步骤> <!-- ev=… -->
- [ ] P2.2 <步骤> <!-- state=in_progress · gate=… -->
- [ ] P2.3 <步骤>

## 关键问题
## 决定
## 错误
```

- **只有两层：阶段 → 步骤。** 没有子步骤。某一步需要补内容时，就在它后面插一步（`plan insert`）。CLI 会拒绝第三层。
- **每个阶段都有步骤**，看板上才点得开：
  - 做完的阶段保留 3~5 条关键步骤，每条写成"做了什么：结果怎样"；
  - 进行中的阶段列出全部步骤；
  - 没开始的阶段至少写出第一步。
- **目标**：整件事做完是什么样，一两句。阶段性目标写进阶段小结，不改这里。
- **现在**：CLI 按步骤状态自动生成，永远和步骤一致；手改会在下次写入时被覆盖。
- **阶段**：3~7 个，一个阶段回答一个问题或交付一样东西。标题后的 ✅ 🔄 ⏸ ⏳ ✕ 由 CLI 按步骤状态写，分别表示完成、进行中、卡住、未开始、放弃。阶段名里不写这类记号。
- **步骤的机器信息**：编号、依赖、验收、证据都放在行尾的 `<!-- -->` 注释里，页面上看不见。
  - 卡住的步骤，原因写一句短话（等谁、等什么，≤30 字）。
  - `no_artifact_reason` 只用于"完成了但没有产物"，不要拿来写说明。
- **关键问题 / 决定 / 错误**：只留仍然有用的几条，每条一句话加链接。

## 写法：人话、主线、承上启下

1. **标题写逻辑，不写技术。** 标题回答"这一步是为了弄清什么/得到什么"。阶段名 ≤24 字，步骤 ≤40 字。方法名、参数、数字、编号、路径统统不进标题。做完的步骤写成"做了什么：结果怎样"，让人扫一眼就知道这条路走通了没有。
   - 示例（差）：`跑 ResNet50+CBAM 在 3 seeds × 5 folds 上的消融`；好：`确认加注意力模块到底有没有用`
   - 示例（做完的步骤）：`确认加注意力模块有没有用：只在小样本时有帮助`
2. **突出主线。** 每一步都要说得出它和目标的关系。跟主线无关的维护、清理、运维琐事，要么单独放进一个"遗留/杂项"阶段，要么不进计划（进日志）。
3. **阶段小结要承上启下。** 每个阶段一两句（≤160 字）：
   - 做完的阶段写"得到了什么，所以下一阶段做什么"；
   - 进行中的阶段写"为什么做，现在到哪"；
   - 没开始的阶段写"要回答什么"。

   小结里可以带一两个关键技术点，更多细节放进细节文章。连着读各阶段小结，要能读出整个项目的来龙去脉。
   - 示例：`三种共享主干的做法都没过，所以只剩一个只读检查，决定要不要再试。`
4. **细节放进细节文章。** `_plan_details.md` 按阶段分节，标题和计划一样写成 `## P<n> <阶段名>`。每节放这一阶段的技术要点、关键数字、实验编号、证据路径和旧编号对照；结论性内容仍按惯例用 `record add finding` 记。这个文件由 AI 自由维护，不经 CLI；计划看板的"细节"标签页会显示它。
5. **换路线就清账。** 不再走的步骤用 `plan cancel` 或 `plan replan` 关掉并写一句原因，整条路线不要了就用 `plan phase cancel`。旧路线的步骤不要一直留在待办里。
6. **下一步必须是计划里的一步。** 想做的事不在计划里，先 `plan add` 把它加进来，再去做。

## 增删改查（短命令 `plan`；写入带并发保护并自动留痕）

`plan help` 一屏速查；不写项目就是当前目录所在的项目；加 `--json` 出原始 JSON。

| 操作 | 命令 | 规矩 |
|---|---|---|
| 看 | `plan`（核心）、`plan 当前 / 上一 / 下一 / 全部 / P3`、`plan P3 --细节`、`plan ls` | 做大决定前先重看 `plan 当前` |
| 看别的项目 | `plan 论文`、`plan 25`（窗口号）、`plan ~/projects/x` | 名字对上多个时会列出候选 |
| 定目标 | `plan goal "一两句"` | 目标变了才改 |
| 加阶段 | `plan phase "阶段名" --summary "为什么做" [--after P3]` | 编号自动取没用过的下一个 |
| 加步骤 | `plan add "一句人话" [--to P3] [--gate "怎样算做完"]` | 默认加到当前阶段末尾 |
| 插一步 | `plan insert P3.2 "一句人话" [--why "原因"]` | 紧跟在那一步后面；新 ID 用字母后缀，不重排编号 |
| 推进 | `plan start P3.2`、`plan done P3.2 --ev "证据" [--commit]`、`plan block P3.2 "等谁/等什么"` | 同一时间只有一步在做 |
| 阶段做完 | `plan summary P3 "得到了什么，所以下一阶段做什么"` | 最后一步完成时顺手写 |
| 改名 | `plan rename P3.2 "新说法"`（给阶段 ID 就改阶段名） | 标题只改说法，不改含义 |
| 删 | `plan cancel P3.2 "原因"`、`plan drop P3 "原因"`、`plan replan P3.2 "为什么换" --with "新做法"` | 不物理删除，关掉并写原因 |
| 记一笔 | `plan note "一句话" [--fail\|--learn] [--on P3.2]` | 进日志，不进计划 |
| 收起 | `plan archive [--keep N]` | 做完的阶段步骤移到 `_logs/plan-archive.md`；看板上点开阶段仍能看到 |
| 检查 | `plan check` | 错误和可读性提醒，每条带改法 |
| 重写整份 | `plan rewrite 草稿.md [--apply] [--accept-dropped]` | 见下一节；也用于大改说法 |

改别的项目要用 `-p <路径|窗口号>`，只写几个字的模糊名字不接受。

## 把旧计划改写成目录格式（一次性，或计划又变得难读时）

1. **读全**：`plan`、`plan 全部`、计划原文，以及最近的 findings / decisions / 日志，弄清项目从开始到现在经过了哪几个大段落。
2. **写目标**：一两句话。
3. **归并阶段**：把历史归并成 3~7 个阶段。每个阶段写一两句承上启下的小结，再列步骤：做完的阶段列 3~5 条关键步骤（"做了什么：结果怎样"，带原证据 `ev=`），不要逐条抄旧任务。
4. **只留还有效的待办，换成新编号**：仍然要做的旧任务，用新编号写进它所属的阶段；过时的不抄进来。
   - 迁移预览会把旧的未关闭任务都列在 `dropped_open` 里，逐条核对：要么已经用新编号写进草稿，要么确认放弃。
   - 旧编号（包括已完成、已归档的）不能拿来指另一件事，否则 `Task:` 提交记录会对不上，CLI 会以 `PLAN_MIGRATE_ID_REUSED` 拒绝。
5. **写细节文章**：把从旧计划里拿掉的技术细节、数字、实验编号、证据路径和新旧编号对照，按阶段写进 `_plan_details.md`。
6. **写草稿**：写到 `_tmp/plan-draft.md`，格式同上面的"形状"（`## 现在` 可以留空，CLI 会生成）。
7. **预览**：`plan rewrite _tmp/plan-draft.md`。
   - 必须没有 errors：做完的阶段没列步骤会报 `PLAN_PHASE_NO_STEPS`。
   - `warnings` 要逐条处理：`PLAN_TITLE_TECHNICAL` 表示标题里混了技术细节，`PLAN_TITLE_LONG` 表示标题太长，另外还有缺小结等。
   - `dropped_open` 要逐条核对。
8. **替换**：`plan rewrite _tmp/plan-draft.md --apply [--accept-dropped]`。
   - 替换前的原文会存进 `_logs/plan-history/`；软链 `_task_plan.before-migrate.md` 指向旧格式原文。
   - 替换后用 `plan` 和 `plan 全部` 核对：只看目标、各阶段标题和小结，应该能讲清来龙去脉。
9. **收尾**：把计划、日志和细节文章一起提交。

## 为什么这样分

- 人和 AI 都主要需要"往哪走"。planning-with-files 在计划变长时，只给 AI 注入目标、下一步、当前阶段和最近几条决定；计划看板默认也只显示这些。
- 我们比上游多的东西（编号、依赖、验收、证据、Git 联动）仍然在，只是藏进注释、详情和细节文章，不挡人的视线。
- 项目往往要跑几个月，这和上游"一个任务一份计划、做完就扔"不同。所以做完的阶段要收起、小结要承上启下，目录才能一直保持一屏看得完。
