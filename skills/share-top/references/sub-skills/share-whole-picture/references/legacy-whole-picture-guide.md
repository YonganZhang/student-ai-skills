# Legacy Whole Picture Guide

旧项目 whole-picture 网页的兼容规则,放在短路由 `share-whole-picture` 之后。这里只保留换一个项目仍然成立的规则;
单个项目的节点清单、指标名、公式和发布地址已移出(来由见 `share-top/references/changelog.md`)。
当前路由以 `../REFERENCE.md` 为准,本文只在维护旧项目的 picture 源、模板或交互时读取。

> **用途**:用户明确要看 HTML 网页时,生成单页项目总览,供用户查验方法与代码、学习当前流程。
> **不是**:单数据可视化 / 论文 figure / 汇报图(走科研绘图技能,本包未包含)。

## 1. 触发与更新时机

- **触发**:用户明示要网页 / HTML / 项目封面 / "把网页推一下"。
- **不触发**:只说 "whole picture / 对齐 / 看一下进展"(通常是让 AI 自己读 TOP 真源,不是要网页);日常代码改动、wiki 例行更新;AI 自己觉得"该给用户看了"。
- **更新时机**:只在关键节点(方法论大改、阶段收尾、投稿前)或用户明确要求时重生成;日常改动不连带重生成,因为网页维护成本高、频繁推 URL 会成为噪音。
- **发布**:只有用户要求发布时,才按所在环境的报告交付 / 文件分享方式发布(发布技能本包未包含),交付后说明数据真源和未确认项。

## 2. 页面结构(参考骨架,按项目取舍)

- 顶部:展开/收起 + 章节锚点导航;TL;DR(项目是什么 / 方法是什么 / 产出是什么);少量关键数字卡。
- 正文可选章节:目标与 gap、方法与创新点、角色/智能体、数据源、流程图(主体)、案例、提示词或核心业务规则、目录结构与测试入口。
- 单页优先:不跳子页(相对路径的子页发布后容易 404);不要为网页自身再加一个 "whole picture" 章节。
- **"漂亮误读"红线**:项目输入混乱、处于早期探索、没有确定数据源时,不套完整模板;先问用户要 facts / assumptions / 待决策清单,否则会编造"创新点"。
- 商业 / 产品项目复用时做语义映射:创新点 → 价值假设 / 差异点;评委/智能体 → 核心业务逻辑角色;数据源 → 数据接入 / API 依赖;案例 → 用户 / 客户案例;提示词 → 业务规则 / 配置。

## 3. 节点内容规范

每个流程节点的详情建议包含:目标 (What) / 动机 (Why) / 原理 (How,公式可用 LaTeX) / 输入 / 输出 / 上下游 / 代码映射(真实 `path::func`)/ 案例 / 状态。

- **标题是当前方法学动作的人话描述**(动词 + 宾语),不是 pipeline 文件名或函数名。示例:`step_04_build_xxx.py` → "给每个对象画统计范围";`compute_xxx_ratio` → "用两级数据之比做下推"。
- **人话与代码分层**:节点标题用人话,代码英文名、模块路径、模型名放在详情里;版本号不写进节点(版本号会让读者和 AI 混淆当前状态)。
- **code 字段只列当前 active 的函数路径**;不列 deprecated、"待迁移"或"供参考"的旧路径。
- **状态 3 档**:✅ 当前 / 🔄 每次必跑 / 🔮 计划中;不细分历史标签。
- **一个方法学动作只有一个节点**;pipeline step 与算法分类指的是同一件事时合并。
- **区分"融合谁"**:fuse / aggregate / combine 在不同层次含义不同(多源融合 ≠ 分项聚合 ≠ 总分合成);写节点前读函数 docstring 和调用方,不按函数名猜语义。
- **公式与输入输出必须对照代码真签名**:改 `input` / `output` / `how` 字段前先查 `def` 签名和 docstring,不凭记忆或语感;用户指出"公式不对"时也先查代码,用户说法与代码矛盾时如实指出,不顺着改。
- **输入输出要精确**:写到具体文件名、具体函数路径、具体指标真名和数据版本;指标清单从代码里的常量定义取,不从记忆复述。
- **案例字段不填没跑过的数**:没真跑通前留 placeholder(如 "📍 待 pipeline 跑通后补 ⏳"),跑通并经用户确认后再填实数。
- **数字与结论标状态**:✅ 真测(代码跑过 / 数据验证)/ ⏳ 示意(历史或论文值,待重跑)/ 🟡 估算(AI 推理,用户未确认)/ 🔴 假设(用户未确认);禁止把 🟡🔴 写成 ✅。

## 4. 只显示当前,不做 changelog

picture 是查验当前方法与代码、学习当前流程的工具,不是变更记录,也不是数据结果展示。

- 节点详情禁止出现:日期、"用户说/拍板/audit"之类引用、历史动词("已修/已改/之前写错")、版本对比、bug 修复记录、已废弃的方法学名。写 "当前 = X",不写 "之前 Y 现在 X"。
- **死的方法学完全消失**:算法或函数退役后,整个节点删除或改写成新方法的身份,不留 "📦 已归档" 标签。
- 历史教训写进 `_wiki-methodology/_top/_findings/`,picture 不引用历史标签。
- 同一原则适用于六合一其他列:wiki 实体写当前定义,registry 列当前注册项;只有 findings 与 `_legacy/` 保存历史。
- 可以在提交前加一个机械检查脚本(如 `picture_clean_audit.py`),用正则扫日期、历史动词、用户引用、项目自定义的废弃方法名,命中即阻止提交;正则清单按项目维护。

## 5. 改方法必须三层对齐

改核心方法学(公式、算法、关键参数、评审规则等)时,完成的定义是三层同时对齐:

| 层 | 查什么 | 怎么查 |
|---|---|---|
| 代码层 `_code/` | 新函数 / 新算法写完 | `git diff _code/` |
| pipeline 层 `_pipelines/` | 主入口确实切换到新函数 | `grep` 主入口脚本里的新函数名 |
| picture 层 | 相关节点详情已更新 | 按节点 key 查 picture 源 |

任一层没改:要么改齐,要么在提交信息里明确写哪层未同步。退役旧代码同理三件套缺一不可:代码 `git mv` 到 `_legacy/<date>-<reason>/`、主入口调用删除、picture 节点删除。
写新函数前先查有没有同语义代码,命中就停下问用户:接进来 / 替换 / 共存。

"只在用户要求时更新网页"与"三层对齐"不矛盾:前者管何时发布,后者管发布时内容必须与代码和 pipeline 一致。

## 6. picture 单一真源:改源再渲染

```text
_whole_picture/
├── picture.yml          ← 唯一人写源(节点 × 字段)
├── picture_audit.py     ← 自检入口,改 yaml 后必跑
├── render.py            ← yaml → HTML(模板渲染)
├── templates/*.html.j2  ← 页面模板
├── head/tail_static     ← yaml 不管的静态段(逃生口)
└── <产物>.html           ← 生成物,不手改
```

- 改内容只改 `picture.yml`,跑 audit(0 error 才渲染)再 render;不直接 grep/sed/Edit 生成的 HTML(下次渲染会覆盖)。
- audit 建议覆盖:schema 完整、key 唯一、code 路径存在、code 函数已在 registry 注册、状态标记合法、跨组连线引用的 key 存在、未出现项目登记的废弃名称。audit 只查机械事实,不查科学语义。
- 节点 schema 最少 `key` + `title`,其余字段为推荐;key 用 `<group_id>.<seq>` 这类稳定前缀,不用中文或版本号。
- 顶部加 `schema_version`,renderer 兼容旧 schema。
- 适用边界:picture 是学习层不是存储层。流程分解、概念、创新点适合放 picture;大量实验结果、长叙事、配置参数、Git 历史各有自己的真源,picture 只放入口。
- 两层架构的好处:结构化数据可 diff("认知漂移"可见)、可复查、渲染不怕一次生成被截断。

## 7. 流程图语义

- **按运行性质分组**:原始数据(起点)/ 预处理(跑一次后复用)/ pipeline 主跑(每次重算)/ 后处理(产出给人看)/ 中间变量(可选)。不要把"代码函数清单"做成一组塞进图里(那是 codemap 的内容)。
- **形状**:方块 = 代码模块 / step;圆 = 中间变量或原始数据。中间变量只选跨多步、跨组使用或公式提及的关键变量,不加 step 内部临时变量。
- **箭头唯一语义 = "X 的输出是 Y 的输入"**:
  - 实线:方块 → 方块,真有数据顺序传递;
  - 虚线(带数据名 label):方块 ↔ 圆,数据经中间变量流转;
  - **平行无依赖的节点不连线**(schema 里标 `parallel: true`,渲染时跳过组内自动串线),否则读者会误以为有先后顺序;
  - 禁止圆 → 圆直连、方块 → 方块用虚线、实虚乱掺。
- **图例必加**:说明方块/圆/实线/虚线/平行不连线的含义。这是经典数据流图(DFD)的简化。

## 8. Mermaid 与交互实践

- **label 净化而不是删图**:Mermaid 报语法错时修 label,不要整块删掉流程图。label 内避免上标字符(`²³`)、嵌套括号、全角括号、嵌套双引号;公式放详情里用 MathJax 渲染。可在 renderer 里做自动净化和截断。
- **结构感知替换**:改详情只替换对应节点块,改函数名只在 `<code>` 内匹配;需要全文替换时先 grep 每个命中,落在 mermaid block / HTML 属性 / JS 字符串里的就改逐节点编辑。
- **同一 HTML 不混用两种编辑方式**:批量改用脚本,少量改用编辑器;混用会导致编辑工具的文件缓存失效。
- **交互跨设备优先原生**:手机 webview 里 mermaid click、JS 抽屉、fixed 定位不稳定时,用 HTML5 `<details>`(`templates/details_native_picture.html`)或 URL hash 深链;JS 字符串里避免中文双引号嵌套,发布前 `node --check` 语法检查。
- **大图缩放**:节点多时用 svg-pan-zoom 只缩放流程图本身(mermaid 异步渲染,需轮询等 SVG 出现再初始化);流程图容器可全宽、高度随视口自适应,文字段保留各自最大宽度。
- **样式克制**:纯 CSS Flexbox/Grid;不写复杂动画、嵌套 SVG 或重 JS 框架(标签闭合易错,维护成本高)。
- **色阶有依据**:用色阶表达等级时,分档边界来自数据分布或领域标准(如官方分级),并在图例写明;没有依据时用连续色标,不自拟固定阈值。

## 9. 模板与数据契约

- 模板:`../templates/details_native_picture.html`(默认,零 JS)、`../templates/binary_tree*.html` + `binary_tree.css`(旧树形模板,兼容用)。树形模板只适合严格的层级分解;流程本质是 DAG(多输入多输出)时用流程图,模块很多时按主题拆成多张图。
- 输入契约(示意):

```yaml
project: {name: "...", abstract: "一句话 TL;DR", stat_cards: [{num: 0, label: "..."}]}
methodology:
  innovations: [{name: "...", motivation: "...", method: "...", reference: "..."}]
data_sources: [{org: "...", desc: "...", url: "..."}]
flow: {groups: [...], nodes: [...]}
cases: {items: [...], metrics: [...]}
prompts: {...}
```

- 骨架锁定、内容动态:章节骨架与状态标记规则固定;卡片数、节点数、启用的章节由数据决定;项目可放局部覆盖配置。
